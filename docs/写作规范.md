# 槐序霁写作规范

本文依据当前主题的数据解析、页面组件与生产预览整理。写文章使用 `docs/posts/`；本文和同目录的《文章模板》是维护文档，不发布为博客文章或站点页面。

实现依据：`.vitepress/theme/posts.js`、`.vitepress/theme/components/MarkDown.vue`、`.vitepress/theme/views/Home.vue`、`.vitepress/theme/views/Post.vue`、`.vitepress/config.js` 与 `post/[slug].paths.js`。若旧 README 的概括与这里不同，以当前实际实现为准。

## 1. 文件、标题与正文层级

文件名统一使用 `YYYY-MM-DD-slug.md`，只放在 `docs/posts/` 的第一层，不使用子目录。Slug 建议为小写英文与短横线，在所有文章中唯一；不要包含句点、斜杠或空格。

例如 `docs/posts/2026-10-23-first-note.md` 对应 `/post/first-note.html`。日期前缀会从访问地址中去掉。发布后尽量不改 slug，改名会改变访问地址；当前没有重定向功能。

文章标题写在 Frontmatter 的 `title` 中，详情页会自动生成一个 H1。正文从 `##` 开始，章节下使用 `###`、`####`，不跳级，不再重复写 `# 文章标题`。标题表达具体内容，段落之间留一行空白，列表项和句子保持简洁。

## 2. Frontmatter 字段

文件开头使用 YAML，以独占一行的 `---` 包住。文字建议加双引号，日期统一写为带引号的 `YYYY-MM-DD`。标题含冒号、井号时尤其需要引号。

| 字段 | 写作要求 | 当前实际用途 |
| --- | --- | --- |
| `title` | 必填，字符串 | 首页、列表、文章 H1 及 SEO 标题；缺省会显示“未命名文章”，不要依赖该回退。 |
| `date` | 必填，有效日期字符串 | 发布日期与文章倒序排列；不是文件修改时间。缺省取解析时的当前日期，不适合正式文章。 |
| `category` | 可选，单个分类字符串 | 聚合分类；不填时卡片显示“未分类”，分类页不会收录到一个自动生成的“未分类”分类。 |
| `tags` | 可选，字符串数组 | 聚合标签；不填相当于空数组。首页和归档列表最多显示前两个标签，详情页显示全部。 |
| `cover` | 可选，图片地址字符串 | 首页卡片与文章详情封面；支持本地路径或完整 HTTPS URL，普通显式地址优先；不填按文章顺序使用本地封面。不是图片对象或数组。 |
| `coverTitle` | 可选，字符串 | 封面标题区域右侧的独立副标；不填留空，不会重复显示文章标题。 |
| `description` | 强烈建议填写，纯文本字符串 | 首页摘要、文章 meta description 与 Open Graph 描述；未填写时取正文第一条非空且不以 `<` 开头的行，并非自动提取“第一段纯文字”。 |
| `hot` | 可选，正整数，通常省略 | 静态热度显示，默认 1；不是实际访问量，写 0 也会回退为 1。 |

只把以上字段当作主题功能。`categories`、`draft`、`published`、`updated`、`lastUpdated`、`seoTitle` 等字段目前没有接入文章展示或筛选逻辑。

## 3. 发布日期与更新时间

`date` 决定排序，文件名日期用于命名约定与 slug 提取；两者应保持一致，但修改文件名日期本身不会调整排序。

修订旧文章时保留原 `date`。当前没有更新时间字段展示，可在正文中手动写：

```markdown
> 最近更新：2026-10-23。补充了本地预览步骤。
```

没有草稿和定时发布过滤：文章只要放入 `docs/posts/`，重新构建后就会收录；未来的 `date` 也不会自动隐藏文章。未准备公开的草稿保存在项目之外或另一个不被扫描的目录，不要用 `draft: true` 代替。

## 4. 分类与标签

每篇文章使用一个主分类，优先复用现有的“项目文档”“使用教程”“部署教程”。可以使用新分类，分类页会自动聚合；新分类的说明和图片默认回退，不需要为发文章修改主题配置。

标签选择少量主题词，通常 1～5 个，按重要性排列，保持命名一致，例如一直使用 `Vue3`，避免混用 `vue3`、`Vue.js` 表达同一个标签。筛选按原字符串精确匹配，系统不会自动合并大小写、别名或空格。

```yaml
category: "前端"
tags: ["Vue", "笔记"]
```

不要把分类写成数组，也不要把标签写成 `tags: Vue, 笔记` 这样的单个字符串；后者不符合当前解析器要求，会影响页面解析。

## 5. 封面与正文图片

优先把图片放到 `docs/public/images/posts/<slug>/`，目录不存在时自行新建。引用从站点资源根路径开始，不包含 `docs/public`：

```yaml
cover: "/images/posts/first-note/cover.webp"
coverTitle: "一次写作记录"
```

```markdown
![说明图片内容](/images/posts/first-note/example.webp "可选图片说明")
```

先放入真实图片再填写路径。封面固定以 16:9 容器裁切，主体靠中间，避免把重要信息放在图片边缘或底部标题区域。正文图片按原比例响应式显示并懒加载；替代文字和可选说明应能解释图片。当前说明渲染会把 Markdown 的 title，或没有 title 时的替代文字，显示在图片下方。

本地图片适合稳定封面、图标与重要资源，已有 WebP 保持可用，不需要强制迁移。也可以给 `cover` 和正文使用完整 HTTPS 图片地址，为未来自建图床保留选择：

```yaml
cover: "https://img.example.com/posts/example.webp"
```

```markdown
![图片说明](/images/example.webp)
![图片说明](https://img.example.com/posts/example.webp)
```

上述域名只是文档示例，不写入真实站点配置。`/images/example.webp` 是站点根相对路径，对应 `docs/public/images/example.webp`；`../images/example.webp` 是页面相对路径，在 `/post/<slug>.html` 下会解析为 `/images/example.webp`。路径相对于发布后的页面，不是 Markdown 源文件；优先使用 `/images/`，不使用 `E:\...` 或 `../posts/...` 推断图片位置。

静态部署不妨碍访问远程图床，但外链依赖网络、证书、防盗链与服务可用性。重要图片优先本地保存，或使用自己能维护的稳定 HTTPS URL；SEO 分享图尤其应避免随机接口。不自动上传第三方图床、不删除本地资源，也不将文章图片放进 `docs/public/img/` 随机背景池。

既有 `https://t.alcy.cc/ysz` 封面会在同次浏览中独立选择并缓存；重复、超时、不可读大小或超预算时使用本地封面，不保证第三方图库绝对不重复。维护说明见 `docs/public/images/covers/README.txt`。

## 6. 摘要

`description` 建议写 1～2 句话，直接说明文章内容，不重复标题，不塞链接、图片、列表或 HTML。当前摘要仍经过 Markdown 渲染，但纯文本最适合首页整张卡片的点击结构。

首页按桌面三行、移动端四行截断摘要，不按固定字符数截断。省略 `description` 时，正文若以 `## 背景` 开头，摘要就可能只显示“背景”，因此正式文章应显式填写。

## 7. SEO 标题与描述

文章 `title` 同时用于列表、H1 和 SEO。生产构建的 HTML 标题为 `文章标题 | 槐序霁`；`description` 同时作为首页摘要、文章 meta description 和 Open Graph 描述，不必重复维护 SEO 字段。

构建阶段通过 VitePress 页面数据生成 Open Graph 标题、描述和 `article` 类型，首份 SSR HTML 已包含这些信息。稳定封面复用 `cover`，本地封面需要正式域名后才输出 OG 绝对地址。当前默认封面 `https://t.alcy.cc/ysz` 是随机接口，不作为稳定分享图；SEO 改用主题 `defaultShareImage` 的本地图片，域名未知时省略该图片地址。其他稳定 HTTPS 封面仍可直接用于 OG，协议相对地址会转为 HTTPS。

站点名称、描述及正式根 URL 统一在 `.vitepress/site.js`。站主确认正式域名后只需填写其中的 `url` 并重新构建，canonical、og:url、sitemap hostname 和 robots 的 Sitemap 地址会统一生成。域名留空时省略这些地址，不使用本地、示例或旧站地址兜底。

模板继续使用现有字段，不添加 `seoTitle`、`seoDescription` 或嵌套 `seo` 对象。日常发布文章无需修改站点配置。

## 8. 常用 Markdown 语法

正文由主题独立的 markdown-it 渲染，不能把 VitePress 默认 Markdown 编译器支持的全部功能直接视为文章能力。

````markdown
## 二级标题

### 三级标题

普通正文，**重点文字**、*适度强调*、~~删除文字~~，以及 `行内代码`。

- 一个无序列表项
- 另一个列表项

1. 第一步
2. 第二步

[外部资料](https://vitepress.dev/)
[站内文章](/post/markdown-writing-guide.html)

> 引用文字；来源可在引用后补充链接。

```js
const message = '槐序初霁，花落满径'
console.log(message)
```

| 名称 | 说明 |
| --- | --- |
| 本地预览 | 保存后检查页面 |
| 生产构建 | 发布前检查输出 |
````

链接显式使用 `[说明](地址)` 或 `<https://example.com>`，不要依赖纯网址自动变成链接。站内文章使用 `/post/<slug>.html`，不要链接到被排除的 `/posts/日期-slug.md`。

代码块写上语言名称有助于阅读和维护；当前文章渲染器主要提供统一代码块外观与转义，并未接入逐词语法高亮、复制按钮或行号，不能把这些作为发布前提。

普通表格、引用、列表可直接使用。数学公式、任务复选框、自定义容器、Vue 组件等扩展当前未在这个文章渲染器中接入；需要表达公式或待办时先用普通文字、代码块或列表，不为单篇写作引入扩展。

## 9. 从创建到发布

1. 复制同目录《文章模板》的内容，新建 `docs/posts/YYYY-MM-DD-your-slug.md`，检查 slug 唯一；不要移动或覆盖已有文章。
2. 修改 `title`、`date`、`category`、`tags` 和 `description`，删去不需要的可选项与提示。正文从 `##` 开始。
3. 把本地图片放入 `docs/public/images/posts/<slug>/`，再填写真实图片路径。不使用自定义封面时保持 `cover` 注释或省略即可。
4. 在项目根目录 `blog` 执行 `npm run docs:dev`，按终端显示的地址打开首页，点击新文章；首次缺少依赖时先执行 `npm ci`。
5. 检查标题、日期、摘要、图片、代码与链接，检查分类和标签筛选；至少查看一次桌面和手机宽度。新增文件后若动态文章地址未出现，重启开发服务再确认。
6. 执行 `npm run docs:build`。构建成功后运行 `npm run docs:preview`，检查新文章地址 `/post/<slug>.html` 能直接打开。
7. 在真实 Git 仓库中只暂存本篇文章及其图片，用中文提交说明；不要混入其他人的修改。当前目录若没有 Git 仓库，只保存并记录，不自行 `git init`。
8. 将 `docs/.vitepress/dist/` 作为完整静态站点交给已有部署流程。只有明确要求时才 push 或执行线上发布；若部署由 CI 负责，按该仓库已约定的授权流程操作。

## 10. 完整示例

文件：`docs/posts/2026-10-23-first-note.md`；访问地址：`/post/first-note.html`。以下正文图片使用仓库现有站点图标演示本地路径；正式写作时换成自己的文章图片。

````markdown
---
title: "第一篇本地写作记录"
date: "2026-10-23"
category: "生活"
tags: ["随笔", "笔记"]
description: "记录在槐序霁中创建 Markdown 文章、检查本地效果与准备发布的步骤。"
coverTitle: "写作手记"
---

## 缘起

把一次小小的实践写下来，方便之后回顾。

## 写作过程

1. 创建文章并填写 Frontmatter。
2. 在本地检查首页、文章、分类与标签。
3. 构建成功后准备发布。

### 示例代码

```js
const title = '第一篇本地写作记录'
console.log(title)
```

### 图片与资料

![站点图标](/assets/apple-touch-icon.png "本地图片路径示例")

[项目介绍](/post/about-huaixuji.html)

| 阶段 | 结果 |
| --- | --- |
| 本地预览 | 页面显示正常 |
| 生产构建 | 构建完成 |

> 把日常写下来，就是给未来留下线索。

## 小结

用明确的标题、摘要和简单段落，让文章容易阅读，也容易维护。
````
